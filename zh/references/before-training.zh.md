# 训练前明确记录内容

## 交流与记录方案

先读取项目需求与当前实验计划，再查看训练入口、loss 实现、配置、MLflow 接入和已有实验记录。向用户呈现已理解的含义，以及真正需要决定的差异。避免让用户重新填写可以从代码获取的信息。

| 需要明确 | 记录内容与含义 | 形式 |
|---|---|---|
| 本次探索什么 | 研究主题、主要改动、基线及关注的对比 | 主题笔记开头、run tags |
| 观察哪些量 | loss 树、评估量、ID/OOD 划分、单位和聚合口径 | 指标字典、metrics |
| 如何观察 | 频率、横轴、对比预设、加权视图开关 | 项目 tracking 配置 |
| GPU 执行效率 | 每卡利用率 >90% 的目标、采样窗口/间隔、阶段边界和有效吞吐单位；按[GPU 采样规范](experiment-execution.zh.md#gpu-利用率采样优化与记录)执行 | `tracking.json.gpu_utilization`、系统指标、原始采样 artifact |
| 主机 RAM 与 I/O | run 允许内存、非缓存峰值/余量、缓存上限、常驻数据及预加载计划 | `tracking.json.memory_cache`、内存/吞吐实测、产物路径 |
| 验证开销与范围 | 固定 10–20% 子集身份、quick/full 频率、缓存安排与选模口径 | `tracking.json.validation_policy`、子集清单、分开的 quick/full 指标 |
| 运行了什么 | 实际配置、训练代码、数据版本和依赖 | params、配置与源码 artifacts |
| 结果保存在哪 | 输入、运行目录、日志、checkpoint、分析结果 | 路径清单、路径图 |

如果还没有明确的成功标准，记录实验目的即可。只对影响当前工作的缺项提问；已经知道的选择直接沿用。训练前输出简短的本次记录方案，然后在已授权范围内接入代码。

本次需要实现或执行变体时，在修改/启动代码前读取[实验执行与隔离](experiment-execution.zh.md)。沿用已明确的预算与 worktree/输出规则；只整理 logging 的任务不启动训练。

## 技术说明与本次差异

读取[项目技术说明](technical-spec.zh.md)与已有项目定义，记录本次基线，以及数据、模型、目标和训练评估协议的变化。沿启动脚本和覆盖关系解析实际配置，区分实际数据与新准备的数据版本，把目标追踪到叶子损失与已发布指标键。启动时将技术说明的版本与代码、配置快照一并保存。

## 身份与生命周期

一个 MLflow experiment 通常对应稳定的项目或训练任务；`study` 表示研究问题，`variant` 表示改进版本，每次具体训练及每个 seed 分别有 run。使用 tags 保存 `study`、`variant`、`baseline_run_id`、`journal.node_id`，随机种子保存为 param。业务标签使用自有命名空间。

执行记录以 `run_id`（或等价的唯一执行 ID）为键，`variant` 用于分组。登记表应保留同配置的重复运行和不同 seed；学习率或 variant 名称不能作为唯一执行身份。

首次配置时复用现有 tracking URI、experiment 和认证方式。记录方案准备好后，在真实训练启动时创建 run，并把 run ID 写入本地运行元数据和路径图。训练、autologging 和手动 logging 共用明确的 run，核对是否产生重复 run。

同一配置和目标的故障恢复可续接原 run，恢复 global step。更改关键配置、目标或数据后的训练创建关联的新 run，注明来源 checkpoint。仅补写分析时使用 client 指定旧 run，不改变它的状态和结束时间。

继承 checkpoint 时，记录实际加载的 checkpoint、父 run 及其身份，模型／优化器／随机状态分别恢复还是重置，以及子 run 的本段和累计训练预算。初始化元数据描述实际载入状态；只有确实使用了预先生成的 seed checkpoint，才将它记为初始化来源。

将训练结果与记录同步状态分开。先保存 checkpoint 和执行结果，再刷新索引、图和报告。训练结束后的附件上传或视图更新失败时，把具体操作记为待同步，基于已保存的元数据补齐；不要因此把已完成训练标为失败，也不要为了修复记录重复优化步骤。保留原 run、指标历史和启动快照；训练本身的异常仍按实际情况记录为失败或中断。

## 元数据分配

| 类别 | 保存位置与内容 |
|---|---|
| 固定超参数 | params：学习率初值、优化器、batch size、有效 batch size、梯度累积、精度、seed、固定 loss 权重 |
| 随时间变化的量 | metrics：学习率、loss 权重、训练进度；GPU 训练还记录逐卡采样利用率、显存、step 耗时和有效吞吐 |
| 完整配置 | artifact：解析默认值、继承和命令行覆盖后的实际配置，包含 loss 定义和记录约定 |
| 数据 | 版本或清单标识、划分、样本数量、预处理及实际路径；沿用现有数据版本机制 |
| 环境 | Python、框架、CUDA、GPU/进程数，已有依赖锁文件或环境导出 |
| 启动 | 训练命令、解析后的入口/cwd、解释器及观察到的模块/本地依赖位置、运行主机、开始时间和时区 |
| checkpoint | 最佳与最终 checkpoint 的位置、step、选择指标和对应结果 |

MLflow params 表达固定事实；可更新的说明用 tags/描述，长文本与完整配置用 artifacts。连接信息记录可分享的地址，认证信息沿用环境配置，不纳入配置导出。

## 训练代码与路径

在真实训练开始时保存 commit、分支、未提交 diff，以及参与训练的本地源码快照，包括尚未提交的新文件。覆盖训练入口、模型、loss、数据处理和本地依赖代码。配置与依赖清单一并保存，方便查看当时运行的版本。

使用代码快照描述未提交修改；仅为日志不要求提交或新建分支。独立开发的变体按执行文档采用 branch/worktree 隔离。启动快照标识历史代码，同时保证活跃任务实际读取的源码和本地依赖直到退出都稳定。后来工作区变化不改写该 run 的 revision。

路径条目包含用途、主机/存储位置、路径或 URI，以及是否上传为 MLflow artifact。大数据和权重按项目的存储约定处理；仅保存远端路径时明确它是外部位置。将分支、代码版本、关键变化及产物与实验路径图关联。

## 接入验证

自定义训练循环通常需要显式记录分量，先检查 autologging 已记录哪些内容。用项目现有的小型运行或最小可行训练/验证片段验证：run 身份正确、关键指标可读回、ID/OOD 名称正确、step 和代码快照对应。多进程训练由指定进程写入汇总结果。

在实际 launcher 环境加入执行文档中的 cwd/import/editable 依赖和可写路径检查。通过后在用户已有授权和预算内执行具体实验，记录真实启动身份和测量结果。
