# 指标含义与比较

## 固定指标字典

训练前读取项目字典，将代码内部变量映射到稳定的 MLflow key。模型版本、日期和改进名称放在 run 名称或 tags 中。同一 key 在不同 runs 中保留同一含义。

每个指标定义：标准 key 或模式、含义、层级、公式及实现位置、单位、mask、归一化与 reduction、聚合分母、适用数据集、权重关系和记录频率。按实际需要填写，重点明确会影响比较的定义。

新字典分别使用 `formula`、`implementation`、`definition_version` 字段；已计算与已记录不一致时补 `computed`/`logged`。维护旧 `formula_or_code` 条目时补齐定义并保留原有定位。

例如：

```text
train/raw/total
train/raw/reconstruction
train/raw/reconstruction/position
train/weighted/reconstruction/position
train/objective
val/id/raw/total
val/ood/raw/total
```

没有 ID/OOD 的项目可以固定用 `val/raw/...`；一旦选定命名，后续沿用。新增数据域时扩充标准 key 并保留已有可比指标。缺少的分量留空。公式或聚合口径改变时明确记录定义版本，必要时使用新的语义 key，并保存共同评估口径以便比较；不把不同定义的同名指标直接当作等价。

叶子公式变化也会改变包含它的每个 group/total 的定义身份。例如 MSE 换为 Huber 时，拟合组和受影响总量也要区分，不能只给叶子换 key。变化的聚合项使用按公式类别命名的稳定 key；未变分量和共同评估键在各变体间继续复用，不把变体名或日期塞进指标名。同步更新字典、适用范围、视图和启动时定义版本。`train/objective` 始终记录各 run 实际优化目标，同时关联其定义；不同目标间用共同评估指标比较。同一个已声明加权公式内只调整配置系数时，记录权重/配置变化，不给所有指标重新命名。

## 原始值、加权值和总量

原始 loss 默认表示完成 mask、必要归一化和 reduction 后、应用损失组合权重之前的值。具体模型中的样本权重、类别权重或重要性采样可能属于 loss 定义，应单独说明，不能仅靠“raw”一词推断。

加权分量表示对实际优化目标的贡献。若父项权重为 α，子项为 β，则子项贡献包含 αβ。总量采用项目明确的公式，不重复累加父项与其子项。定义不出有意义的原始总量时，记录已有分量及实际 objective，并说明总量选择。

`train/objective` 始终记录实际用于反向传播的目标。动态权重以 `weights/<component>` 记录曲线，初值与调度规则保存为配置。跨权重方案比较优先查看定义一致的原始量和评估指标；需要共同总分时，另行约定固定参考权重。

## 四类视图

| 视图 | 内容 |
|---|---|
| 训练原始损失 | 总量、所有分量和标量细分量 |
| 训练加权损失 | 总量、各层分量的加权贡献 |
| 验证原始损失 | 同上，ID/OOD 同一分量默认同图 |
| 验证加权损失 | 同上，ID/OOD 同一分量默认同图 |

加权视图支持 `auto/on/off`。`auto` 在非平凡多项加权或动态权重需要观察时启用，曲线基本重复时省略；关闭视图仍保留实际训练 objective。验证有明确的加权目标时才记录对应加权值。逐样本、逐 token 等大规模明细按需保存附件。

将这些分组保存在 `tracking.json.loss_views`，包含稳定的视图 ID、指标模式、层级（`total`、`group`、`leaf`）和验证域配对。`weighted_views` 仅保存展示策略枚举，公式写入指标字典。下文五种比较预设用于在这些视图中选择 runs 和指标，不能替代四类视图。

接入时，为每个启用的视图提供可用入口：保存的 MLflow 布局、生成的页面或命令，或当前 UI 中具体的打开步骤。用真实 run 逐个检查，总量、组和标量叶子均可查看，验证中同一分量的 ID/OOD 成对展示。仅写入指标命名空间或 `loss_views` 配置不算完成视图交付。后续实验开始使用非平凡权重时，随指标字典一并更新这些入口。

## 采样、聚合和横轴

记录频率复用项目设置；缺省时先按训练成本提出一个具体建议，与用户一次确定，不把固定频率强加给所有项目。训练记录区分当前 batch 值和窗口统计，并固定含义。

默认 `step` 是优化器更新次数，epoch 另记。验证记录使用被评估模型对应的 step。按本次声明的完整评估范围（固定小验证子集或全量验证集）和约定分母聚合；多卡先汇总分子、分母，再求均值，避免不等长 batch/rank 的均值直接平均。ID/OOD 分别聚合，需要总体值时明确组合比例。

batch size、梯度累积或序列长度变化时，可记录 `progress/samples_seen`、`progress/tokens_seen` 作为训练量对齐依据。历史曲线完整保留，平滑仅用于展示。

## 常规子集验证与定期全量验证

尚无既定评估协议的新实验，常规检查使用**固定 10–20% 验证子集**，通常每个 epoch 一次。各数据域按任务、长度或少数子群等相关因素分层选择，保存 seed、样本 ID、数量、比例及清单/哈希；可比较的变体复用同一子集。重要子群覆盖或指标稳定性不足时扩大范围，10–20% 是起始建议，不是统计保证。按执行文档的 RAM 预算常驻或提前加载。

每隔**计划总 epoch 数的 2.5%**做一次全量验证，并在 final checkpoint 做全量验证。启动前按 `max(1, ceil(planned_total_epochs * 0.025))` 解析间隔：200 epoch 时每 5 epoch 一次。将计划总量和解析后的 `full.every_epochs` 保存到 `tracking.json.validation_policy`；从 run 开始累计已完成的 epoch，恢复训练后继续沿用。按步数预算训练时，按计划总 optimizer updates 解析等价间隔。正式实验即使 epochs 较少，也保留最终全量评估，准备阶段的小型 smoke 检查仍按其限定范围执行。将某 checkpoint 作为正式报告的 best 前，用约定的全量验证范围复核候选；另行明确 early stopping/调度使用 quick 还是 full 指标，以及 patience 按什么次数计算。已有明确评估协议继续沿用，主动调整时记录协议变更。这里的全量指验证集，不是留出的 test 集，也不要求重复读入已缓存的数据。

quick 与 full 曲线分开：已有全量键继续使用 `val/{dataset}/raw/{loss}`，子集使用 `val_quick/{dataset}/raw/{loss}`，加权指标同理。每次评估关联范围身份与实际评估数量。跨变体沿用相同命名和子集清单，quick 对 quick、full 对 full；四类损失视图和对比预设明确标注/选择范围，正式结果比较默认 full。摘要与 best checkpoint 报告注明结果来自哪个范围。

## 快捷比较

项目保存五种预设：跨改进同指标、单 run 的 ID/OOD、跨改进的 ID/OOD、分量之间、同分量加权前后。支持用户直接说“对比 baseline 和这次改进的 ID/OOD 总 loss”。先解析明确的 runs、指标和横轴，再生成结果。

每种适用的预设提供可使用的入口，例如保存的 UI 视图、链接或可传入所选 runs 的简短命令，并用真实记录的指标执行检查；仅在 `tracking.json` 写一个名称不算快捷入口。预设重复或不适用时，在入口说明原因，不把缺失数据展示成有效比较。

四类视图是逻辑展示分组，不承诺 MLflow 存在四个原生页面。检查已安装版本支持的多指标图、布局及保存方式，优先复用可用界面。没有适用的自动布局接口时，给出具体配置步骤或通过公开 API 获取 metric history 生成对比图；不要声称写入命名空间会自动创建页面或快捷键。

对比图标明 run、数据域和分量，保持一致的横轴与平滑设置。数量级或单位不同的分量可用并排图；根据本次分析需要选择。按同一个 checkpoint、final 或已定义的 best 口径生成表格，并注明使用哪一种。
