# 在隔离 worktree 中执行实验变体

用户要求实现、运行或比较模型/代码变体时，使用本流程。先读取当前需求、主题笔记、共享路径图和项目执行约定。实现和启动前读取[项目技术说明](technical-spec.zh.md)、[训练前与元数据](before-training.zh.md)、[指标与比较](metrics-and-comparison.zh.md)和[实验路径图](experiment-map.zh.md)，聚焦本次变体的定义、日志、对比与溯源规则。复用这些规范，不另建一套日志体系。

## 研究问题、对比与预算

在主题笔记明确研究问题、基线、各变体差异、可比较的评估协议和预期观察。沿用用户已授权的资源与范围：变体、seeds/重复次数、更新步数或 epochs、算力/时间预算、并发数及停止条件。真正影响执行的缺项集中补齐一次，不给每次启动增加一轮审批。要求执行实验通常已包含为该实验创建常规 branch/worktree 和完成小测试。只整理日志或地图本身不授权正式训练；如果仅授权准备，就交付已准备、已测试的状态，如实记录。

## 选择隔离单元

| 工作 | 代码工作区 | 执行身份 |
|---|---|---|
| 独立开发的代码/模型变体，包括并行 agents 修改代码 | 默认分别建立 branch + worktree | 每次实际执行分别有 run |
| 同一冻结代码版本的 seeds 或重复运行 | 可复用一个 worktree | 每次独立 run、seed/配置快照和输出目录 |
| 固定代码的配置 sweep | 可复用一个 worktree，各自解析配置 | 每个 trial 独立 run、实际配置和输出目录 |

复用已有合适的 worktree。沿用项目命名；没有约定时可用 `codex/<study>-<variant>` 分支，以及约定 worktree 根下的同级目录。创建前核对已有分支和路径；并行 agents 分别独占各自变体的可编辑目录。一个 run 不等于一个 worktree，分支名也不是不可变代码版本。

运行中的任务所读取的源码应保持稳定直到退出，包括延迟导入的模块和本地依赖。后续变化在其他工作区准备，或从完整冻结的执行副本启动并核实路径/import。启动源码归档只用于溯源，不能隔离仍在读取可编辑目录的进程。固定代码 worktree 可并发运行的前提是所有参与者都不再改这份代码。

## 保留真实起点

识别基线仓库、准确 commit、相关 worktree 状态，以及作为预期基线所必需的 staged、unstaged、untracked 训练源码/配置/本地依赖。干净的 `git worktree add -b <branch> <path> <baseline-commit>` 只包含该 commit，不会自动带上用户未提交的修改。

未提交修改属于本次起点时，先在源树外保存带版本身份的源码快照、可覆盖二进制的 staged/unstaged patches，以及相关 untracked 文件的清单和副本。将该状态还原到隔离目录，保留内容和删除情况，在修改变体前与捕获的起点核对。基线身份记为 commit **加上**快照/patch 身份，不把它描述为干净 commit。不要仅为隔离而 stash、reset 或 commit 用户源树。哪些未提交修改属于实验仍不清楚时，继续不依赖该选择的准备，只询问这一项。

启动时按既有 revision/源码快照约定另存实现后的变体。后续修正产生新 revision，也保留原始源树和基线证据。

## 实现、小测试与启动

在各自 worktree 中实现计划差异，更新受影响的技术说明和指标定义，使用项目已有小测试或有界 smoke run 验证真实路径。区分这些检查和正式预算中的实验 runs。检查通过后，在既有授权范围内执行完整实验；用户已要求执行且具备条件时，不停在计划阶段。

在实际执行主机的真实 launcher 环境核实隔离：解析后的 cwd 与入口、解释器、训练/模型/数据模块的实际导入位置（`__file__` 或等价方式）、本地 editable installs 和配置路径。新 worktree 若仍通过解释器或 editable 依赖导入另一工作区，就没有实现隔离。只有导入与可变本地依赖解析正确时才复用环境，否则使用各 worktree 独立环境或显式本地依赖路径并验证。将观察到的位置与启动命令、revision 一起记录，不能只凭 shell 初始目录判断。

只读数据和上游 checkpoint 可以共享，并记录版本身份。各 run 的可写输出、日志、checkpoint、临时文件和可变缓存分别隔离。只有缓存 key 已包含相关数据/代码/配置身份且写入与并发协议可靠时才共享缓存，否则隔离。相对路径按实际启动目录解析，核对输出不会覆盖基线、其他 run 或共享日志。并发 trials 不轮流改写同一配置文件，各自传入或保存解析后的配置。

实际启动时保存 execution/job 身份、可获得的 run ID、代码/配置/技术说明快照、输入身份、输出路径及预算。有真实启动回执才记为 `running`；提交的作业可能仍在排队。失败和中断按观察记录；训练结果和日志上传/渲染状态按[训练前与元数据](before-training.zh.md)区分。

## 主机内存预算与数据缓存

构建或启动实验前，明确**本 run 最多可占用多少主机 RAM、其中多少用于缓存**，与 GPU 显存分开记录。逐主机记录用户/作业/容器内存上限、当前可用 RAM、其他任务占用约定、非缓存部分的预期峰值和运行余量。预算覆盖 rank/worker 副本、组 batch 与预取队列、pinned buffers，以及验证/checkpoint 的峰值。预加载前落实以 GiB 表示的 run 预算与缓存上限；不能只用数据文件大小估计解码后的内存占用。将实测预算与缓存方案保存到 `tracking.json.memory_cache` 和 run 快照。

GPU 实验默认逐主机按 **`total_ram_gib * 0.95 * run_gpu_count / total_gpu_count`** 分配 RAM。记录主机总物理 RAM、整台主机的物理 GPU 总数，以及本 run 在该主机获配的 GPU 数；分母不取进程可见卡数。多机分别计算。例如 512 GiB、8 卡主机使用 2 卡，默认份额为 121.6 GiB。先乘 95% 再按卡数分配，使互不重叠的显卡配额合计最多对应整机 95% RAM。这是本 run 在该主机全部 ranks/workers 的合计上限，不给每个进程重复分配，也不要求占满。

实际 run 预算还受用户/作业/容器上限，以及扣除其他任务承诺后的主机可用容量约束。用户可明确覆盖比例份额，记录覆盖值和原因，并遵守整机上限与实际资源限制。缓存额度按 **`cache_cap_gib = max(0, run_budget_gib - non_cache_peak_gib - headroom_gib)`** 计算。同时保存比例计算值和最终 run/缓存预算，便于区分默认分配、实测限制与用户覆盖。

优先用预算减少训练 I/O：缓存反复使用的训练数据/特征，按需选择共享只读内存、mmap/系统页缓存或有界缓存，避免每个 rank/worker 各复制完整数据。随机增强仍按训练协议执行，确定性预处理缓存记录版本。数据放不下时缓存热点、其余分块读取；保留余量，避免 swap 或内存压力拖慢训练。

常规验证把[指标与比较](metrics-and-comparison.zh.md)定义的固定 10–20% 子集常驻内存，或在验证前提前加载。重要验证集（例如 OOD）只有在内存充足且**训练已无 I/O 瓶颈**时，才考虑全量常驻。缓存范围和验证频率分别决定：全量驻留不等于每个 epoch 都全量计算。后台预取受缓存预算与训练吞吐约束；全量验证继续复用已有缓存，只读取缺失部分。

代表性短测及后续性能检查中，与 GPU 利用率一起采样主机/作业内存、可用 RAM、数据等待耗时或磁盘读取速率、step 耗时和有效吞吐；记录缓存实际占用、预加载耗时及调整前后吞吐。原始测量随 run 保存，Markdown 保留允许/峰值 RAM、常驻数据或子集清单、瓶颈及采用策略。以预算内实测吞吐提升为准，不以占满内存为目标。

## GPU 利用率：采样、优化与记录

GPU 训练必须实测利用率，原则上**稳态训练期间每张已分配 GPU 的时间加权平均利用率应超过 90%**。这里指 GPU 计算活跃度（例如 NVML / `nvidia-smi` 的 `utilization.gpu`），不是显存占用比例或某一次峰值。同时报告包含验证、checkpoint 保存的整个执行窗口均值，并标明阶段；训练中的数据等待、分布式同步仍计入训练窗口。

正式预算运行前，用预期模型、数据加载、精度和单卡 batch 做有界的代表性训练短测。默认预热后**每 1 秒采样一次，持续 120 秒**。已授权短测更短时，保留实际时长和样本数，不写成完整窗口。训练期间默认**每 5 秒采样一次**；性能相关配置变化或持续低利用率后，再做细粒度窗口采样。复用 NVML、`nvidia-smi` 或已有监控，核实实际采样间隔与聚合方式。将这些约定保存到 `tracking.json.gpu_utilization`，随 run 留配置快照。

覆盖每个主机上所有已分配设备。记录时间戳、主机、GPU UUID/设备映射、利用率%、已用/总显存及 run/进程关联；可获得时对齐训练阶段和 optimizer step。共享卡的整卡利用率不能代表本 run。利用率同时配合 step 耗时和有效吞吐（样本/token/残基每秒，注明单位）；低利用率时按实际情况检查加载耗时、通信及功耗/时钟限制。

原始采样以 CSV/JSONL 保存在 run 目录，并作为 MLflow artifact 上传或关联路径。时间序列使用项目稳定的系统指标键写入 MLflow；默认 `system/gpu/{device}/utilization_pct`，设备身份包含主机。每张卡、每个阶段/窗口汇总实际时长、样本数、时间加权均值、p10，以及利用率不高于 90% 的采样时间比例；不能用多卡平均掩盖空闲卡。Markdown 只保留主要利用率/吞吐结果、瓶颈、调整前后实测和原始数据路径。

低于目标时，定位瓶颈，在既定预算内调整并按可比条件重新采样。优先检查数据加载/缓存/预取、无必要的 CPU–GPU 同步、算子执行及负载均衡。优化以有效吞吐提升且实验含义一致为准；改变有效 batch、精度、目标或评估协议时，按实验配置变更记录。预算内仍未达标时，记录实测差距、原因、已尝试调整和本次采用配置，供用户决定后续投入。利用率是执行效率目标，与实验的科研成败分开记录。

## 代码派生与权重继承

来源路线/revision 解释代码派生，不证明加载了该路线的权重。独立记录实际加载的 checkpoint 和父 run、初始化与 resume 语义、model/optimizer/scheduler/step/随机状态分别恢复还是重置，以及本段/累计预算，复用已有 checkpoint 约定。适用时明确随机初始化。变体关系用研究派生/比较边，真实 checkpoint 使用用 `uses_model` 依赖边；两者都有证据时同时保留。

## 唯一日志、真实结果与历史保留

所有 worktree 使用同一个绝对路径 `tracking.json.record_root`、MLflow tracking backend/experiment、证据索引、主题笔记和路径图。规范根目录应稳定，放在可清理实验树之外，或有明确保留安排。不能让各 worktree 跟踪的 `experiments/` 副本变成互不相干的日志，也不能用相对 `mlruns` 把 runs 写到不同位置。backend/存储方案应支持预期的并发写入。

先写入持久化的各 run 独立事件/元数据。共享 JSON、Markdown 和图采用项目单一写入者，或共享锁覆盖重新读取、按稳定 ID 合并、原子替换及从合并状态渲染。合并不同 revisions/runs/events，不拿工作进程的旧整份文件覆盖刚更新的地图。相同更新机制保留用户笔记和人工布局。未接入后台更新时补齐待处理事件，无需另造调度框架。

在[实验路径图](experiment-map.zh.md)维护 baseline → variant → revision/run 关联；追加实际 run 和 revision，不替换旧 trials。按约定协议和预算比较实际测量结果，如实说明未完成 trials，再与用户讨论解释。用户要求保留或已明确的发现和后续决定再写入记录。比较后不自动合并或删除实验分支/worktree，记录各路线的继续工作入口。按各文档实际所在目录检查交付报告和接续说明的链接，包括从主题笔记复制过来的 Markdown 链接。
