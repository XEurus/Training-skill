# 已有项目初始化

初始化把已有代码、历史训练和分散证据整理成可继续维护的实验记录。先建立完整纲要和已有内容，再与用户补充真正影响记录方式的选择。复用现有目录、指标名、MLflow experiment 和文档结构。

## 1. 确定范围并盘点

从当前项目、用户指定的分支或实验范围开始。先读项目说明、AGENTS.md、训练入口、配置、已有笔记和运行元数据，再按线索检索。大型日志先读取索引、摘要和指标文件，避免一次遍历所有 checkpoint 或数据内容。

| 来源 | 收集什么 | 用来确定什么 |
|---|---|---|
| Git 和 worktrees | 当前及相关历史分支、commit、差异、已有工作区位置 | 哪条路线改了什么，代码如何关联 |
| 训练代码与配置 | 模型入口、loss 树、权重、评估划分、超参数 | 记录内容和含义 |
| MLflow | 可访问的 experiments/runs、params、metrics、tags、artifacts | 历史训练身份、结果与代码快照 |
| 本地或已连接存储 | 日志、配置快照、运行清单、checkpoint 元数据、评估表和图 | 补足已有证据及产物位置 |
| 现有文档与用户说明 | 实验目的、已写明的发现、决定和基线 | 研究主题、当前认识与历史结论 |

Git 历史用只读命令查看，不为了盘点切换分支。无法访问的远端来源记为待接入，先完成可访问部分。已有本地历史无需先迁入 MLflow 才能纳入索引。

## 2. 先解释项目，再建立索引

读取[项目技术说明](technical-spec.zh.md)。识别活跃研究路线及其实际启动配置，沿每种不同执行链追踪样本、模型、优化目标、评估与模型选择。选择代表性 run 并读取对应源码快照，历史归档路线单独概括。依据已有计划解释每条活跃路线的问题和相对基线的变化。

在可复用的项目文档中填实八类技术内容：提供连贯的端到端解释，写清形状/单位与依赖、公式及实现定位、归属到具体 run 的实际配置。复用完整的专题文档并补足缺项。新推断的研究解释仍留在交流中。

在 initialization.md 中记录技术覆盖：类别、已查明什么、来源/版本、说明位置和具体缺失证据。它体现分析覆盖程度，而不仅是创建了哪些文件。区分已有结果、实现行为、计划变更和用户决定。

## 3. 形成整体纲要

先生成或更新 `requirements.md`，明确记录本项目当前的需求。它是后续实验的工作依据；`initialization.md` 记录如何组织和接入这些内容，两者通过链接关联。

需求记录包含：当前目标与优先问题、用户希望获得的结果、记录内容及其含义和形式、已确定约束、已有依据，以及尚需讨论的具体选择。已有成功标准或验收方式就写入，没有则记录目标即可。依据来自用户说明和现有需求文档；代码和日志用于说明现状，AI 提出的新增需求标为“待讨论”，不把当前实现直接当作用户要求。

把已经明确的信息写入文件，并注明来源或证据 ID，不只创建空模板。项目已有满足这些用途的文档时沿用其路径。单个实验的需求写入 `notes/<study>.md` 的“当前需求与本次计划”：关注问题、预期观察、基线、本次改动和记录方式，并链接项目需求。用户后续明确调整目标、优先级或记录内容时，更新当前需求，简短保留日期与变更原因。

根据盘点结果起草 `initialization.md`，用表格说明每个研究主题：关心的问题、记录项、含义/计算口径、数据来源、保存形式、对比视图和更新时机。把已有信息填实，不只交付空模板。

同时整理项目级默认：实验命名和归组、指标字典、四类视图、ID/OOD 关系、路径位置、代码快照方式、checkpoint 口径、笔记结构及主动维护触发点。将代码中已确认的定义和已有项目约定直接填入；对歧义给出建议，并集中讨论少量影响结果的选择。用户已经确定的内容无需再确认。

填写 `tracking.json` 时读取[指标含义与比较](metrics-and-comparison.zh.md)。四类损失视图（`train_raw`、`train_weighted`、`validation_raw`、`validation_weighted`）与五种比较预设（`variants`、`id_ood`、`id_ood_across_variants`、`components`、`weight_effect`）分别保存。每类视图包含总量、分组及全部标量叶子，缺失值明确标出。`weighted_views` 保持为 `auto`、`on` 或 `off`；公式和权重说明放入指标字典。视图与预设使用具体指标 key 或可解析的模式，不同训练/评估流程的可用指标不同时分别说明。

制定执行约定时读取[实验执行与隔离](experiment-execution.zh.md)，即使本次只初始化记录。将实际规则写入 `tracking.json.execution` 或已有项目约定：worktree 根目录、分支/路径命名、基线 commit 及 dirty/untracked 保留方式、固定代码的 seeds/sweeps、运行期间源码稳定性、环境/import 验证、各 run 输出/缓存范围、资源预算默认及归属/并发方式。先查看已有位置，在本次确定可复用的默认，以后只讨论变化。

项目存在多个 worktree 时，确定一个共享记录根目录，把实际位置写入各工作区使用的项目约定。实验代码可以位于不同分支，索引和路径图仍汇总到同一处。复用现有共享位置；没有既有位置时选择一个稳定位置并说明，必要时与用户讨论。

规范日志根应稳定，放在可清理变体树之外，或明确其保留方式。所有变体使用相同的绝对 MLflow tracking 位置/backend 和 experiment。明确共享记录的单一写入者或共享锁，覆盖重新读取、合并、原子写入和渲染；各 run 事件在合并前持久保留。

在共享目录的 `tracking.json.record_root` 中保存本机可访问的绝对路径；各工作区 AGENTS.md 管理段写入相同路径，并直接读取其中的配置与索引，不各自复制一份。初始化覆盖到哪些工作区，就更新哪些工作区的入口；尚未访问的工作区列为待接入。

不同历史记录使用不同指标名称时，先记录别名和定义映射。只有含义与聚合口径一致才纳入同一比较；保留原始记录，后续训练逐步使用项目标准名称。

## 4. 建立证据索引与历史关联

保存 `evidence.json`，结构为 `schema_version: 1`、`sources: [...]`。每条 source 至少包含：

- `id`：稳定标识。
- `kind`：git、config、metric、artifact、document 或 user_statement。
- `location`：文件路径、URI、run 引用或可定位的用户说明；可补 `host`。
- `locator`：commit、文件行号、JSON key、metric key/step 或文档章节等具体定位。
- `observed_at`：本次收集时间；有原始实验时间时另用 `recorded_at`，未知为 null。
- `supports`：该证据直接支持的事实、数值或已有结论摘要。
- `node_ids`：对应的实验节点。

以证据关联分支、代码状态、runs、产物和已有发现。使用现有 run ID 和节点 ID 去重；一个 run 的多份文件合并到同一记录。原始执行状态未知时使用 `unknown`，历史代码未知时保留未知 revision。无法确认 tracking URI 的历史 run 先作为证据条目记录，补齐后再关联正式 run。

已有文档中明确记载的结论可以保留，并标明其来源和历史日期。AI 新推导的收益判断留在讨论中。来源冲突时同时保留具体出处，并把需要澄清的差异列入纲要。

## 5. 构建可维护的项目记录

按已知内容建立或增量完善以下文件：

| 文件 | 初始化后应有的内容 |
|---|---|
| `requirements.md` 或已有需求文档 | 项目当前需求、优先事项、记录内容/含义/形式、约束、依据和待讨论项 |
| `initialization.md` | 记录纲要、盘点范围、重要缺项和需讨论的选择 |
| `specs/data.md`、`model.md`、`objective.md`、`training-eval.md` 或复用文档 | 八类技术内容、实际执行流、来源/版本与具体 run 差异 |
| `tracking.json` | 现有 MLflow 配置、指标字典、频率、路径及对比预设 |
| `evidence.json` | 可定位的历史证据索引 |
| `experiment-map.json` | 研究路线、分支、代码版本、runs、路径，节点可附 `evidence` ID 列表 |
| `experiment-map.excalidraw`、`.md` | 包含改动/结果、模型/数据依赖、代码与产物入口的可视路线，以及同源完整路径表 |
| `notes/<study>.md` | 主题实验的当前需求与计划，以及已有主要结果、注明来源的发现和当前认识 |

首次初始化先整理已有事实。只有用户要求历史数据迁入 MLflow 时，再按来源和原始时间导入；仅构建索引不重写旧 runs，也不把补录时间伪装成训练时间。后续训练需要的 logging 接入按训练前流程完成。

把项目主动维护约定合并到 AGENTS.md 的 `<!-- experiment-journal:start -->` 管理段，内容参考项目 hook 模板，并替换为实际记录路径。已有管理段只更新该段，其他内容保留。这样后续实验任务在收尾时会主动更新记录和路径图。

重复初始化时根据稳定标识合并增量，保留用户笔记、图上的手动布局和批注。已有事实没有变化时不重复创建记录。

## 6. 交付

交付前检查：读者能否复述主线执行流、找到各损失定义、区分当前/run/计划版本，并确认主要结果的评估协议。对照代码及一份代表性配置/结果核对说明；JSON 与链接校验只覆盖格式。核对记录方案保留四类损失视图和五种比较预设，且每一项都能定位到已定义指标或明确的待补项。待补项写具体来源，不附加泛化的防御性段落。

交付时链接到已填好的需求记录和整体纲要，展示已覆盖的主题/分支/runs、可打开的 Excalidraw 图和少量待明确事项。说明哪些来源已读取、哪些尚未接入。下一次使用先读取当前需求，从这些约定继续，不重新做一次全项目盘点。
